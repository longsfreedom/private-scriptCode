## 1. 整体方案
本项目采用「结构化错误报告 + 统一日志 + 守卫/恢复机制」的组合方式，没有定义自定义异常类型或全局错误码表。核心思路是：各子系统（截图、模板匹配、OCR、输入）在独立 try/except 中捕获异常并累积为字符串消息，最终由 `PlatformValidator` 汇总成 `PlatformValidationReport` 返回给调度器；调度器根据报告字段决定状态迁移，并通过 `GuardManager` 的超时/重试守卫触发 `RecoveryManager` 的分级恢复流程。所有运行时问题通过 `src/utils/logger.py` 提供的单例化 logger 写入 `runtime/logs/automation.log` 与控制台。

## 2. 关键文件与职责
- `src/modules/env_module.py`：定义 `PlatformValidationReport` dataclass（包含 `passed`、`screenshot_ok`、`template_ok`、`ocr_ok`、`input_ok`、`errors`、`next_step_suggestions` 等字段），并在 `run()` 中对每个子链路分别 try/except，将异常信息以字符串追加到 `errors` 列表，不中断其他链路的检查。
- `src/core/scheduler.py`：主循环入口，调用 `GuardManager` 检测超时，调用 `PlatformValidator.run()` 获取报告，遍历 `report.errors` 逐条 `logger.error` 输出，并根据 `report.passed` 驱动状态机迁移。
- `src/core/guards.py`：`GuardManager` 提供 `is_retry_exhausted`、`is_state_timeout` 两个纯函数式守卫，依赖 `ScriptContext.state_retry_count` 与 `state_elapsed_seconds()` 判断是否达到最大重试或状态超时。
- `src/modules/recovery_module.py`：`RecoveryManager` 提供三级恢复 `try_light_recovery` / `try_medium_recovery` / `try_heavy_recovery`，其中重型恢复会设置 `manual_required=True` 并转入 `MANUAL_REQUIRED` 状态。
- `src/utils/logger.py`：`get_logger(name, log_dir)` 使用模块级 `_LOGGER_CACHE` 缓存 Logger，自动创建 `runtime/logs` 目录，同时附加控制台与文件处理器，格式固定为 `%(asctime)s | %(levelname)s | %(name)s | %(message)s`。
- `disaster_advice_agent.py`：独立的农业气象 LLM 调用脚本，对 `urllib` 的 `HTTPError`、`URLError` 捕获后包装为 `Exception` 抛出，顶层 `try/except Exception` 打印错误。
- `src/input/contracts.py`：接口契约类中的方法直接 `raise NotImplementedError`，作为未实现接口的占位错误。
- `src/utils/windows_api.py`：底层 Windows API 失败时构造 `OSError(f"... last_error={ctypes.get_last_error()}")` 向上抛出。

## 3. 架构与约定
- **错误聚合而非立即失败**：`PlatformValidator.run()` 将截图、模板匹配、OCR、输入四个子链路各自 try/except，即使某一项失败仍继续执行后续链路，最终通过 `passed = screenshot_ok and template_ok and ocr_ok and input_ok` 给出整体结果。
- **错误以字符串消息形式传递**：`errors: list[str]` 是唯一的错误载体，没有自定义异常类；上层只消费字符串列表并记录日志。
- **守卫-恢复分离**：`Scheduler` 负责检测超时/重试耗尽，`GuardManager` 只做布尔判断，`RecoveryManager` 负责实际恢复动作（写 metadata、切换状态），三者解耦。
- **人工接管兜底**：重型恢复强制进入 `MANUAL_REQUIRED` 状态，主循环检测到该状态后停止自动流程。
- **日志即错误出口**：除结构化报告外，所有错误路径均通过 `self.logger.error(...)` 落盘，便于事后排查；无统一的错误码枚举。
- **顶层入口统一退出**：`main()` 返回 `int` 退出码，由 `raise SystemExit(main())` 统一暴露给操作系统。

## 4. 约定与约束
- 所有需要可配置日志输出的模块必须通过 `get_logger(name, log_dir=...)` 获取 logger，禁止自行 `logging.getLogger`。
- 环境校验类代码不得因单个子链路异常而中断整体检查，应捕获异常并追加到 `errors` 列表。
- 状态机相关逻辑不得直接 raise 业务异常，应通过 `ScriptContext.transition_to(...)` 配合 `GuardManager` 守卫进行状态迁移。
- 网络请求类外部调用（如 `disaster_advice_agent.py`）需显式捕获 `HTTPError`、`URLError` 等具体异常，再包装为通用 `Exception` 向上传播。
- 未实现的抽象接口方法统一 `raise NotImplementedError`，用于开发期快速暴露缺失实现。
- 平台底层 API 失败时使用 `OSError` 并附带 `ctypes.get_last_error()` 以便诊断。

## 5. 局限
- 没有自定义异常层次结构，错误语义仅靠字符串消息表达，不利于程序化区分错误类型。
- 错误来源定位依赖日志中的 logger name 和消息文本，缺少结构化 error_code 字段。
- 恢复策略目前仅为 stub（`return True` 或跳转状态），尚未接入真实的重启/回滚逻辑。
